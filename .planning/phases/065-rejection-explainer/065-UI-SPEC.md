## Spacing Scale

Declared values (multiples of 4):

| Token | Value | Tailwind Class | Usage |
|-------|-------|----------------|-------|
| xs | 4px | `space-y-1`, `gap-1`, `px-1` | Icon-to-text gap within inline elements; shortlist section spacing |
| sm | 8px | `py-2`, `px-2`, `gap-2` | Vertical cell padding, inline badge padding |
| md | 16px | `px-4`, `py-4` | Standard card padding (unused by existing panels this phase) |
| lg | 24px | `space-y-2` (8px gap between sections, not 24px — see note) | Section gap within expand panels |
| xl | 32px | n/a | n/a this phase |
| 2xl | 48px | n/a | n/a this phase |
| 3xl | 64px | n/a | n/a this phase |

**Explicit exceptions (matching existing component patterns — not introducing new values):**

- `space-y-0.5` (2px) — exception: matches existing `ExplainPanel.tsx` line 14 vertical rhythm for rejection/reason list items (`<ul className="space-y-0.5">`). Phase 65 preserves this value in WHY-01 and WHY-03 rejection line lists to match the surrounding component pattern.
- `px-3` (12px) — exception: matches existing `ExplainPanel.tsx` container padding (`px-3 py-2`) and `GemTable.tsx` mobile expand row cell padding (`px-3 py-3`). Phase 65 uses `px-3` on the new desktop expand row cell to match the existing mobile expand row exactly.

Note on `space-y-2`: Tailwind `space-y-2` = 8px, not 24px. The lg token (24px) is declared for completeness but `space-y-2` correctly belongs to the sm scale. The table above reflects correct Tailwind-to-pixel mappings.

## Component Specifications

### WHY-01: GemTable Desktop Expand Row

**Trigger:** `getRowCanExpand: () => true` — all rows on all screen sizes (D-01, CONTEXT.md).

**Desktop expand row** (`sm:block` / not `sm:hidden`):
- Background: `bg-blue-50 dark:bg-blue-950` (matches mobile expand row — visual consistency)
- Cell: `colSpan={row.getVisibleCells().length}`, padding `px-3 py-3`
- Content: rejection panel ONLY — no hidden column data (D-02, CONTEXT.md)
- No action-sheet buttons (Compare/Dismiss are desktop-header actions, not needed here)

**Mobile expand row** (existing `sm:hidden` row — preserved unchanged per D-03):
- Action-sheet (Compare/Dismiss) rendered first
- Hidden column data `<dl>` rendered second
- Rejection panel appended BELOW hidden column data (D-03)

**Rejection panel structure** (shared between desktop and mobile):
```
<div className="mt-2 space-y-1">
  <p className="text-xs font-medium text-zinc-500 dark:text-zinc-400">Why not recommended:</p>
  <ul className="space-y-0.5">
    {rejectionLines.map(line => <li className="text-xs text-zinc-600 dark:text-zinc-400">{line}</li>)}
  </ul>
</div>
```

Note: `space-y-0.5` (2px) in the `<ul>` is an explicit exception — matches the existing `ExplainPanel.tsx` line 14 pattern (`<ul className="space-y-0.5">`). `px-3` on the expand row cell is an explicit exception — matches `GemTable.tsx` line 216 mobile expand row cell padding.

For strong players with no rejection signals:
```
<p className="text-xs text-green-700 dark:text-green-400">
  No rejection signals — ranked #X at [POS] by xPts (Y.Y pts projected)
</p>
```

### WHY-02: TransferPanel High-Ownership Callout

**Placement:** Between the Load Squad form and the OpportunityCostTable (D-11). Rendered only when squad is loaded and at least one qualifying player (≥20% ownership, absent from transfer candidates) exists.

**Container:**
```
<div className="rounded border border-zinc-200 dark:border-zinc-700 bg-zinc-50 dark:bg-zinc-800 p-3 space-y-1">
  <p className="text-sm font-medium text-zinc-700 dark:text-zinc-300">
    ℹ️ Why aren't these players appearing?
  </p>
  {/* one <p> per qualifying player, capped at 3 */}
  <p className="text-xs text-zinc-600 dark:text-zinc-400">
    [PlayerName] ([X]%): [reason sentence]
  </p>
</div>
```

Note: `p-3` (12px) on the callout container is an explicit exception — matches the existing `ExplainPanel.tsx` container padding pattern (`px-3 py-2`).

**Component name (Claude's discretion):** `HighOwnershipCallout` — concise, describes the trigger condition.

**Capped at 3** by `selected_by_percent` descending (D-13). `parseFloat(player.selected_by_percent)` required (string field).

### WHY-03: ExplainPanel Rejection Section

**New prop:** `rejectionReasons?: string[]` on `ExplainPanel`.

**Rendered only when** `rejectionReasons` is non-empty and defined.

**Position:** Below existing positive `<ul>` of reasons, above "Replacement options" shortlist (D-08).

**Markup:**
```
{rejectionReasons && rejectionReasons.length > 0 && (
  <div className="space-y-1">
    <p className="text-xs font-medium text-zinc-500 dark:text-zinc-400">Why not recommended:</p>
    <ul className="space-y-0.5">
      {rejectionReasons.map((reason, i) => (
        <li key={i} className="text-xs text-zinc-600 dark:text-zinc-400">{reason}</li>
      ))}
    </ul>
  </div>
)}
```

Note: The wrapping `<div>` uses `space-y-1` (4px) between the header `<p>` and the `<ul>`. The `<ul>` itself uses `space-y-0.5` (2px) between list items — explicit exception matching the existing `ExplainPanel.tsx` line 14 pattern for reason lists.

Fragility lines within `rejectionReasons` that come from `computeFragility()` are plain strings (e.g., "no longer recommended if: start_prob < 70%") — they render as body text, not inside `<FragilityNote>`. The amber-coloured `<FragilityNote>` pattern belongs to TransferPanel and CaptainPicksPanel contexts (Phase 64). In ExplainPanel the same content is presented as a plain text rejection line matching the existing `text-xs text-zinc-600 dark:text-zinc-400` style.

**String formatting rules (Claude's discretion):**
- Position codes: "GK", "DEF", "MID", "FWD" (uppercase, matching existing usage in codebase)
- Rank label format: "ranked #X at [POS]" (lowercase "ranked", hash prefix, uppercase position code)
- Percentages: integer only via `Math.round()` (e.g. "23%", not "23.4%")
- xPts values: one decimal place via `.toFixed(1)` (e.g. "7.2 pts projected")
- Player names: `web_name` field (not `full_name`)

## Adaptive Framing Threshold (Claude's discretion)

The boundary between "show rejection reasons" and "show positive framing" uses **gem_score relative to position average**:

- Compute position average `gem_score` via `computePositionAverages()` from `src/lib/recommend.ts`
- If `player.gem_score >= positionAverage.gem_score` AND `computeFragility()` returns no reasons AND start_prob >= 0.70: → positive framing ("No rejection signals — ranked #X…")
- Otherwise: → rejection reasons (ordered per D-07: rank, start_prob, fixture, fragility, ownership context)

This mirrors the `computeExplanations()` threshold pattern in `src/lib/explain.ts`.

## File Location (Claude's discretion)

`computeRejection()` lives in `src/lib/explain.ts` — alongside `computeExplanations()` as the negative counterpart. A separate `rejection.ts` file would create unnecessary module fragmentation given they share threshold constants.

## Accessibility

- All rejection text is plain text in `<li>` / `<p>` elements — screen-reader accessible without ARIA additions
- ℹ️ in WHY-02 header is decorative — no `aria-hidden` required (it's part of visible copy, not supplemental)
- `⚠` in FragilityNote has `aria-hidden="true"` (established pattern in `FragilityNote.tsx`) — if fragility text is rendered as plain string in ExplainPanel, no aria-hidden needed
- Touch targets: expand rows are triggered by row click (inherited from GemTable `onClick` on `<tr>`) — no new tap targets introduced below 44px
