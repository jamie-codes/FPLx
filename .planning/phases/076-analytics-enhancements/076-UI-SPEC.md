# Phase 76 — UI Design Contract

> Visual and interaction contract for three loosely-coupled additions: a `routes_to_points` GemTable column (RTP-02), an Accuracy GW drill-down (ACC2-01), and a LineupTab captain/VC override (OPT-01). Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This phase extends three existing components within the established design language. The contract below codifies conventions already in use across `GemTable`/`columns.tsx`, `AccuracyTab.tsx`/`FixtureSwingDetector.tsx`, and `LineupTab.tsx` so the planner/executor stay consistent. **No new design tokens, no new colours, no new fonts.** Every choice has a verbatim in-repo precedent (`cs_prob_1gw` column for RTP-02, `FixtureSwingDetector` accordion for ACC2-01, swap state machine for OPT-01).

## Copywriting Contract

This phase introduces three discrete UI surfaces, each with its own copy contract. Strings below are **canonical** — planner/executor must use them verbatim.

### RTP-02 — Routes column

| Element | Copy |
|---------|------|
| Column header | `Routes` |
| Column header tooltip (`H('Routes', ...)`) | `Routes to points (0–5): distinct point-scoring routes — penalty taker, direct FK taker, corner taker, above-median xG in team, above-median xA in team. Higher = more ways to score.` |
| Cell — integer 0..5 | render the digit verbatim (`0`, `1`, `2`, `3`, `4`, `5`) — see "Zero rendering" below |
| Cell — null / undefined (pre-deploy cache) | em-dash with muted colour: `<span className="text-zinc-400">—</span>` (mirrors `cs_prob_1gw` cell at `columns.tsx:373`) |

**Zero rendering decision (resolves RESEARCH Open Question A1):** `0` is rendered as the digit `0`, NOT as an em-dash and NOT clamped to 1. Reasoning:
- The em-dash is reserved for **absent data** (`null` / `undefined` from a stale cache), not for **a meaningful zero**. Mixing the two would teach the user that "—" sometimes means "0" — confusing.
- Clamping to floor=1 inflates the bottom of the distribution (every player would read at least 1) and hides the most useful signal: players with no point-scoring routes are exactly the players the user should NOT transfer in.
- The header tooltip says "0–5" (not "1–5") to match the spec's "counting distinct routes" language. This is a deliberate deviation from the requirement's "integer 1–5" wording — to be confirmed in discuss-phase. Default to 0–5; the planner can flip to 1–5 with a one-line `Math.max(routes, 1)` clamp if the user disagrees.

| GW summary row — disclosure chevron | `▾` (collapsed) · `▴` (expanded) — visible inline after the GW number, e.g. `GW32 ▾` |
| Drill-down panel — Haulers section heading | `Haulers (≥10 pts)` |

**Threshold definitions (resolves RESEARCH Open Question A2):**
- **Hauler** = `actual_pts >= 10` filtered from `data.haulters` by `gw === expandedGw`. Reuses the existing `HAULTER_THRESHOLD = 10` from `pipeline/accuracy.py:27`.
- **Flagged Miss** = `g.xpts_flagged === true && g.actual_pts <= 2` from `data.players[].gws[]` filtered by `gw === expandedGw`. Reuses the existing `xpts_flagged` boolean (model put player in predicted top-N) AND a strict actual-blank threshold of ≤2 pts (matches the canonical "blank" definition used elsewhere in the project).

**Row format (both sub-tables):** `{player_name}` (left, `text-sm`) · `{actual_pts}` (centre, `text-sm tabular-nums`) · `{xpts_predicted.toFixed(1)}` (right, `text-sm tabular-nums`). Three columns. No team abbreviation, no fixture info — names and numbers are sufficient density for this drill-down. Sort: descending by `xpts_predicted` (most-loved-then-blanked first for misses; highest-predicted-haul first for haulers — this surfaces the most informative outliers).

### OPT-01 — LineupTab captain/VC override

| Element | Copy |
|---------|------|
| Set C pill — label | `Set C` |
| Set C pill — `aria-label` (idle) | `Make {player.web_name} captain` |
| Set C pill — `aria-label` (already captain) | `Captain` (and rendered as visually disabled / inert — the current captain's Set C pill is replaced by the static C badge logic) |
| Set VC pill — label | `Set VC` |
| Set VC pill — `aria-label` (idle) | `Make {player.web_name} vice-captain` |
| Set VC pill — `aria-label` (already vc) | `Vice-captain` |
| Captain-armed inline affordance | none — the amber ring + tint IS the affordance. No separate "Confirm captain?" text appears (matches the existing swap arm pattern, which has no inline confirmation copy either). |
| Reset button — label (preserved) | `Reset` |
| Reset button — `aria-label` (preserved) | `Reset to recommended lineup` |
| Reset button — extended behaviour announcement (screen reader, optional) | not added in this phase — the existing `aria-label` covers both swap reset and captain reset (semantically: "reset to the recommended lineup" includes captain) |

**Interaction copy decision (resolves RESEARCH Open Question A3 + A7):** The recommended UX is **always-visible per-card "Set C" and "Set VC" pills** below the captain/VC badges, NOT a separate "armed mode". Reasoning:
- Always-visible pills are direct dispatch (single tap → commit). No two-state arm/commit needed for captain (which would conflict with the existing swap arm/commit and require mutual exclusion logic).
- Discoverability: the pills are visible at all times so the feature is found without a tutorial.
- Touch-target compliance: `min-h-[44px]` per pill is satisfied by `px-2 py-1 text-xs` with explicit `min-h-[44px]` (Phase 75 OwnedFilterToggle precedent).
- The PlayerCard becomes ~12px taller (`min-h-[88px] sm:min-h-[96px]`) to fit the pill row beneath the existing name/xpts/start% block. Multiple-of-4: 88, 96.

**However, the requirement states "tapping a player arms captain assignment".** To honour the literal wording, the contract defines a two-tier interaction:
1. **Default tap on PlayerCard body** (the existing onClick area) keeps its existing behaviour — tap a starter to arm a swap, tap a bench player as the swap target. This is unchanged.
2. **Tap on the dedicated "Set C" pill** (a new sub-button on each card, separate hit area from the card body) commits captain immediately to that player. The "tapping a player arms captain" wording in the spec is interpreted as "tapping a player's captain control arms-and-immediately-commits", which is the cleanest tactile reading. The amber ring still appears briefly (~150ms transition) to confirm the change, then settles into the static C badge.
3. **Tap on the dedicated "Set VC" pill** commits vice-captain immediately.

This interpretation avoids a separate captain-arm state machine that would conflict with the swap state machine and creates a clean tactile path: PlayerCard body = swap; Set C pill = captain; Set VC pill = VC. The user does not need to learn a new "arm-then-tap-elsewhere" flow.

**Captain == VC collision rule (RESEARCH Pitfall 3):** When the user presses Set C on the current VC, the override commits captain to that player AND moves VC to the previous captain (auto-shuffle). When the user presses Set VC on the current captain, the press is a no-op (VC cannot be captain — `aria-label="Vice-captain — already captain"` for the visually-disabled state). This avoids both badges on the same card.

**Destructive actions:** none. Reset is constructive (restores defaults). No confirmation dialog. No data loss path.

## Pitfall: Nested `<button>` Elements

**Problem:** HTML disallows `<button>` nested inside another `<button>`. The current PlayerCard is a single outer `<button>` (`LineupTab.tsx:43–73`). Phase 76 needs Set C / Set VC pills as separate `<button>` elements (independent click targets, independent keyboard focus, independent `aria-pressed` state).

**Resolution:** Refactor PlayerCard's structure so the card body and the pills are SIBLINGS inside a parent `<div>`, not parent/child:

```tsx
// BEFORE (existing — single nested button)
<button onClick={onTap}> ... name + xpts + badge ... </button>

// AFTER (Phase 76)
<div className="relative flex flex-col items-stretch ..." data-testid={`pitch-card-${id}`}>
  <button
    type="button"
    onClick={(e) => { e.stopPropagation(); onTap(id) }}
    className="..."
    data-testid={`pitch-card-body-${id}`}
  >
    ... name + xpts + start% ...
  </button>
  {/* Static C/VC badges — absolute-positioned over the card body, preserved */}
  {isCaptain && <span className="absolute top-1 right-1 ..." data-testid="captain-badge">C</span>}
  {isViceCaptain && <span className="absolute top-1 right-1 ..." data-testid="vc-badge">VC</span>}
  {/* New: Set C / Set VC pill row, sibling of the body button */}
  <div className="flex gap-1 mt-1">
    <button data-testid={`set-c-${id}`} ...>Set C</button>
    <button data-testid={`set-vc-${id}`} ...>Set VC</button>
  </div>
</div>
```

The existing test `data-testid="pitch-card-${id}"` selector continues to work (now on the parent `<div>`); the body-tap target gets a new `data-testid="pitch-card-body-${id}"` for tests that specifically click the body. Existing tests that fire `click` on `pitch-card-${id}` rely on event bubbling (the `onClick` lives on the inner body button) — for safety, the `<div>` parent gets a `onClick` pass-through that defers to the inner button when the click target is the div itself (not the pills). Simpler: tests can be updated to target `pitch-card-body-${id}` explicitly. The planner picks the migration path.
