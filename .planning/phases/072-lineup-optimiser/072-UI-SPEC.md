# Phase 72 — UI Design Contract: Lineup Optimiser

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This phase carries forward the design system established in Phases 58/60 (Mini-League Rival Tracker / Transfer Route Tree) unchanged. Every spacing, typography, and color decision below mirrors prior phases. The new visual surface is a **classic FPL-style pitch layout** with a two-tap swap interaction; the data fetching, empty/loading/error/BGW shell is reused verbatim from `OptimiserPanel.tsx`. No new component library, no new icon library, no new design tokens.

## Spacing Scale

Declared values (multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline padding (`gap-1`, `px-1`) |
| sm | 8px | Compact element spacing (`gap-2`, `px-2`, `py-2`) |
| md | 16px | Default element spacing (`gap-4`, `p-4`, `space-y-4`) |
| lg | 24px | Section padding (`space-y-6`, `mt-6`) |
| xl | 32px | Layout gaps (`space-y-8`) |
| 2xl | 48px | Major section breaks |
| 3xl | 64px | Page-level spacing |

Exceptions for this phase:

- **Touch targets:** every interactive player card sets `min-h-[64px]` (16 × 4 px) on mobile and `min-h-[72px]` (18 × 4 px) on `sm:` and above. Each card is a `<button>` so it satisfies WCAG 2.5.5 (≥44px) with comfortable headroom. Cards must be tap-friendly because the interaction is two-tap, not drag.
- **Reset button touch target:** `min-h-[44px]` (11 × 4 px) — matches the "Load into Manual Planner" button in Phase 60 and the "Load Squad" button in Phases 58/59. WCAG 2.5.5 compliant.
- **Pitch row vertical gap:** `space-y-2` (8 px) between rows — tight enough to read formation at a glance, loose enough that the captain badge does not collide between rows.
- **Pitch card horizontal gap:** `gap-2` (8 px) on mobile, `sm:gap-3` (12 px) on `sm:` and above. Cards never overflow on mobile because each row holds a maximum of 5 cards (DEF/MID legal max). 5 cards × ~64 px width + 4 × 8 px gap = 352 px — fits inside a 360 px mobile viewport with `px-2` outer padding.
- **Bench row separator:** `border-t border-zinc-200 dark:border-zinc-700 mt-4 pt-4` — visually breaks bench from XI without using a heavy section heading.
- **Card inner padding:** `px-2 py-2` (8 px / 8 px). Cards display three lines of text (web_name / xPts / start_prob) at small sizes so generous interior padding is unnecessary.
- **Captain / VC badge inset:** `top-1 right-1` (`absolute` positioned, 4 px inset). The badge is a `<span>` overlaid on the card — does not affect card height.

Source: 058-UI-SPEC.md spacing scale; 060-UI-SPEC.md spacing scale; ChipSquadView player rows (`py-1.5`, `px-1`); OptimiserPanel section spacing (`mt-6`, `space-y-3`).

- **Helper text / footnote** ("Tap a starter, then tap a bench player to swap. Reset restores the recommendation."): `text-xs text-zinc-500 dark:text-zinc-400 italic`. Matches the BB notice italic helper pattern (`OptimiserPanel.tsx:494`).

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#ffffff` / `#0a0a0a` | Page background (`bg-white dark:bg-zinc-900`), pitch background |
| Secondary (30%) | `zinc-50` / `zinc-800` | Player card surface, bench row tinted area, position-row label band |
| Accent (10%) | `zinc-900` / `zinc-100` (Reset button) + `amber-400` ring (pending-swap) + `green-500` ring (legal-swap target) | Reset CTA + pending-swap selection ring + legal-target ring |
| Destructive | `red-600` / `red-400` | Error message text only — no destructive actions in this phase |

Accent reserved for (explicit list — never "all interactive elements"):

1. **Reset button** (default state) — `bg-zinc-900 dark:bg-zinc-100 text-white dark:text-zinc-900 font-semibold rounded min-h-[44px] px-3 py-2 text-sm hover:bg-zinc-800 dark:hover:bg-zinc-200 cursor-pointer`. Same zinc-inverse pattern as the Phase 58 "Load Rivals" button, the Phase 59 "Load Squad" button, and the Phase 60 "Load into Manual Planner" button. The ONE primary CTA on this screen.
2. **Pending-swap ring** — when a starter card is armed: `ring-2 ring-amber-400 ring-offset-1 ring-offset-white dark:ring-offset-zinc-900`. Amber is reused from the existing soft-warning amber palette (`OptimiserPanel.tsx:429`) but at ring strength rather than fill. Amber is correct because the pending state is "you are mid-action, awaiting input", not error and not success.
3. **Legal-swap target ring** — when a bench card is a legal swap target during a pending-swap: `ring-2 ring-green-500 ring-offset-1 ring-offset-white dark:ring-offset-zinc-900`. Green-500 matches the success/positive convention used across `OptimiserPanel.tsx:91` (`xPts gain`), `ChipSquadView.tsx:80`, and the comparison delta pill. Ring (not fill) keeps the card content readable — the user still needs to read the player name to choose.
4. **Captain badge text colour** (`text-amber-600 dark:text-amber-400`) — locked from `SquadView.tsx:162`. NOT considered "general accent" because it is a status indicator on already-rendered data, not a CTA.

Accent is NOT used for: position-row labels, the headline row metric numbers, hover states on idle cards, the bench border separator. These use neutral zinc text.

Semantic / status colours (NOT accent — carried forward from prior phases):

- **Pending-swap selected card** (the armed starter itself): `bg-amber-50 dark:bg-amber-950 ring-2 ring-amber-400` — soft amber tint plus the accent ring above. Distinguishes the source of the swap from its candidate targets.
- **Legal-target bench card during pending-swap:** `ring-2 ring-green-500` (no fill change). Card content remains the standard `bg-zinc-50 dark:bg-zinc-800`.
- **Incompatible bench card during pending-swap:** `opacity-40 cursor-not-allowed` — dim filter, NOT colour change. Locked from prior conventions: `OptimiserPanel.tsx:200` uses `opacity-60` for bench rows under non-BB modes, and `SquadView.tsx:148` uses `opacity-50` for bench rows. We use `opacity-40` to make incompatibility visually clearer than ordinary bench dimming.
- **Bench-row default tint** (no pending-swap): `bg-zinc-50 dark:bg-zinc-800/40`. Subtler than the secondary surface so the eye still distinguishes XI from bench but does not treat bench as visually equal weight.
- **BGW-soft warning banner** (>= 11 eligible but < 15): reuses Phase 47/55 amber container — `rounded border border-amber-400 bg-amber-50 dark:bg-amber-950 px-3 py-2 text-sm text-amber-800 dark:text-amber-200`. Identical to `OptimiserPanel.tsx:429-435`.
- **BGW-critical warning banner** (< 11 eligible — no lineup possible): same amber container but with an explicit `Warning:` prefix — verbatim copy from `OptimiserPanel.tsx:359-363`.
- **Error banner** (squad fetch failed): `rounded border border-red-300 bg-red-50 dark:bg-red-950 p-4 text-sm text-red-700 dark:text-red-300`. Identical to `OptimiserPanel.tsx:332-336`. NOT amber — actual error.

Borders: `border-zinc-200 dark:border-zinc-700` (cards' outer border, banner outer border); `border-zinc-100 dark:border-zinc-800` (bench separator, inner row dividers).

Dark-mode surface pattern (project standard):

- `bg-white dark:bg-zinc-900` — page-level surface, pitch outer container.
- `bg-zinc-50 dark:bg-zinc-800` — player card surface, position-row label band.
- `text-zinc-900 dark:text-zinc-100` — primary text (player names).
- `text-zinc-500 dark:text-zinc-400` — muted / helper text (start_prob percentages, position labels, footnote).

## Component Inventory

### Visual Hierarchy (Focal Point)

- **No-squad state:** Page heading + empty-state copy + (no input — Team ID input lives on the Decision/Transfers tabs per the project's lifted-`submittedId` pattern). The empty-state copy directs the user to load a squad on the Transfers tab. There is no CTA on this screen in the no-squad state — the user must navigate elsewhere first.
- **Loading state (squad submitted, fetching):** Single inline `Loading squad…` text replacing the pitch region.
- **BGW-critical state (< 11 eligible):** Amber warning banner is the visual anchor — no pitch rendered. Identical UX to `OptimiserPanel`.
- **Lineup-rendered state (typical):** The pitch is the primary visual anchor. The captain card carries the amber `C` badge and is naturally drawn higher up the eye-path because it is in the FWD or MID row (top of pitch). The Reset button is the secondary affordance, placed top-right above the pitch. The footnote is the tertiary affordance, below the pitch.
- **Pending-swap state (one starter armed):** The armed card carries an amber tint + amber ring; legal bench targets carry a green ring; incompatible bench cards dim to 40 % opacity. The eye is funnelled to the green-ringed bench cards — the only valid next action.

### Layout choice — pitch grid

The pitch is a vertical stack of 5 rows (GK / DEF / MID / FWD / Bench). Each row is a `flex justify-around gap-2 sm:gap-3` container. No CSS grid — flex with `justify-around` produces the correct equal-spacing-with-edge-margin look that approximates a football pitch row. The pitch itself sits on top of the standard page background — no green field colour, no field lines. Reasoning: a literal pitch background introduces colour-contrast hazards in dark mode and does not pass the accent budget. The "pitchness" is conveyed entirely by the row layout (formation lines).

```
<section data-testid="lineup-tab"> Lineup tab root
├── Heading row: "Optimised Lineup" + Reset button (right-aligned)
├── (Optional) BGW soft warning banner — when eligibleCount < total >= 11
├── HeadlineRow: "Formation: 4-3-3 │ Captain: Salah │ Total xPts: 64.3"
├── Pitch container (onClick={handleBackgroundTap})
│   ├── GK row
│   ├── DEF row
│   ├── MID row
│   ├── FWD row
│   └── Bench row (visually separated by border-t)

```

#### `PitchRow` (sub-component, may be inlined inside `LineupTab.tsx`)

```tsx
function PitchRow({
  position, ids, playerMap, pendingStarterId, legalBenchIds,
  onCardTap, captainId, vcId, isBench = false,

  position: 'GK' | 'DEF' | 'MID' | 'FWD' | 'Bench'
  ids: number[]
  playerMap: Map<number, MergedPlayer>
  pendingStarterId: number | null
  legalBenchIds: Set<number> | null   // null when no pending swap

  captainId: number
  vcId: number

  return (

      </div>

            id={id}
```

#### `PlayerCard` (sub-component — recommended to extract for reuse and isolated testing)

```tsx
'use client'
import type { MergedPlayer } from '@/lib/types'

interface PlayerCardProps {
  id: number
  player: MergedPlayer
  isPending: boolean
  isLegalTarget: boolean
  isIncompatible: boolean
  isCaptain: boolean
  isViceCaptain: boolean
  onTap: (id: number) => void
}

export function PlayerCard({
  id, player, isPending, isLegalTarget, isIncompatible, isCaptain, isViceCaptain, onTap,
}: PlayerCardProps) {
  const baseCls = 'relative flex flex-col items-stretch justify-center min-h-[64px] sm:min-h-[72px] w-full max-w-[96px] sm:max-w-[112px] rounded border bg-zinc-50 dark:bg-zinc-800 px-2 py-2 text-left transition-shadow'

  const stateCls = isPending
    ? 'border-amber-400 bg-amber-50 dark:bg-amber-950 ring-2 ring-amber-400 ring-offset-1 ring-offset-white dark:ring-offset-zinc-900'
    : isLegalTarget
    ? 'border-zinc-200 dark:border-zinc-700 ring-2 ring-green-500 ring-offset-1 ring-offset-white dark:ring-offset-zinc-900 cursor-pointer'
    : isIncompatible
    ? 'border-zinc-200 dark:border-zinc-700 opacity-40 cursor-not-allowed'
    : 'border-zinc-200 dark:border-zinc-700 cursor-pointer hover:bg-zinc-100 dark:hover:bg-zinc-700'

  return (
    <button
      type="button"
      onClick={(e) => { e.stopPropagation(); onTap(id) }}
      disabled={isIncompatible}
      data-testid={`pitch-card-${id}`}
      data-pending={isPending ? 'true' : undefined}
      data-legal-target={isLegalTarget ? 'true' : undefined}
      className={`${baseCls} ${stateCls}`}
    >
      <span className="text-sm font-semibold text-zinc-900 dark:text-zinc-100 truncate">
        {player.web_name}
      </span>
      <span className="text-xs font-semibold text-zinc-700 dark:text-zinc-300">
        {(player.xPts_1gw ?? 0).toFixed(1)}
      </span>
      <span className="text-[10px] text-zinc-500 dark:text-zinc-400">
        {Math.round((player.start_prob ?? 0) * 100)}%
      </span>

      {isCaptain && (
        <span
          className="absolute top-1 right-1 text-xs font-bold text-amber-600 dark:text-amber-400"
          data-testid="captain-badge"
        >
          C
        </span>
      )}
      {isViceCaptain && (
        <span
          className="absolute top-1 right-1 text-xs font-semibold text-zinc-500 dark:text-zinc-400"
          data-testid="vc-badge"
        >
          VC
        </span>
      )}
    </button>
  )
}
```

Notes:
- `e.stopPropagation()` on every card click is REQUIRED (Pitfall 7 of `072-RESEARCH.md`) — the pitch container's `onClick` would otherwise fire and immediately disarm the pending state.
- `disabled={isIncompatible}` makes the button unfocusable AND non-clickable for keyboard users. The `cursor-not-allowed` class is for sighted users; the `disabled` attribute is for assistive tech.
- The card is a `<button>` (not a `<div onClick>`) for a11y — it must be focusable and Enter/Space-clickable.
- `data-pending` and `data-legal-target` are HTML data attributes (only present when truthy) so RTL tests can assert on them without colliding with class-name strings.

#### Mobile element-hiding strategy

NO columns are hidden on mobile. The pitch is a vertical-stack-of-rows layout that scales naturally because the maximum row width is bounded by the legal max formation count (5 cards per row). Each card has `max-w-[96px]` on mobile, so 5 × 96 + 4 × 8 = 512 px — too wide for a 360 px viewport, BUT `flex justify-around` with `flex-1` on the row container forces cards to share the available width equally. On a 360 px viewport with `px-2` outer pad, each card is ~64 px wide. That is acceptable: web_name truncates with ellipsis, xPts and start_prob remain readable. The Reset button stays in place top-right.

The position label column (`w-10` = 40 px) is preserved on all viewport sizes — losing it would make formation harder to scan on mobile.

The footnote stays a single line on desktop and may wrap to two lines on narrow mobile — `flex-wrap` is implicit in the natural text flow.

## Interaction Contracts

### Tab activation

1. User taps "Lineup" sub-tab in the Squad section nav.
2. `activeSection === 'squad' && activeSubTab === 'lineup'` evaluates true.
3. `<LineupTab teamId={submittedId ?? ''} />` mounts.
4. Inside `LineupTab`: hooks fire (`useSquad`, `usePlayers`); `useMemo` computes `initialLineup = optimiseLineup(picks, players, 1)`; `useState<OptimisedLineup | null>(initialLineup)` holds the displayed lineup.
5. `useEffect(() => setLineup(initialLineup), [initialLineup])` syncs override state when underlying data refetches (Pitfall 6 — accept refetch resets as session-only behaviour per D-08).

### No-squad branch

1. `submittedId === null`: render the empty state.
2. Empty-state copy: heading `Optimised Lineup` + body `Enter your FPL Team ID on the Transfers tab to see your optimised lineup.` (Note: this differs from `OptimiserPanel`'s `Enter your FPL Team ID to see your optimised lineup.` because the Lineup tab does NOT host its own input — Team ID input is shared across tabs via the lifted `submittedId` state.)
3. No pitch, no headline, no Reset button.

### Loading branch

1. `isLoading === true`: render `Loading squad...` (verbatim from `OptimiserPanel.tsx:317`).
2. No pitch, no headline, no Reset button.

### Error branch

1. `squadError !== null`: render the red error banner with `errorMessage` (verbatim from `OptimiserPanel.tsx:329-336`).
2. No pitch, no headline, no Reset button.

### BGW-critical branch (< 11 eligible)

1. `lineup === null && eligibleCount < 11`: render the amber `bgw-banner-critical` (verbatim from `OptimiserPanel.tsx:357-363`).
2. No pitch, no headline, no Reset button — there is no XI to display.

### BGW-soft branch (>= 11 eligible but < 15)

1. `lineup !== null && eligibleCount < total`: render the soft amber banner ABOVE the pitch (verbatim from `OptimiserPanel.tsx:427-435`).
2. Pitch and Reset button render as normal.

### Tap a starter (arm)

1. User clicks a card in any of the 4 XI rows (GK / DEF / MID / FWD).
2. Card's `onClick` fires → `e.stopPropagation()` → `onCardTap(id)`.
3. Handler: `if (pendingStarterId === id) setPendingStarterId(null)` (re-tapping disarms) `else setPendingStarterId(id)`.
4. Visual response (single render):
   - The armed card flips to `bg-amber-50 dark:bg-amber-950 ring-2 ring-amber-400`.
   - Bench cards re-render: those that pass `isLegalSwap(lineup, pendingStarterId, benchId, playerMap)` get `ring-2 ring-green-500`. Those that fail get `opacity-40 cursor-not-allowed`.
5. Compatibility computation: `legalBenchIds` is a `useMemo`-computed `Set<number>` derived from `pendingStarterId` and the current `lineup`. Recomputed only when those change.

### Tap a bench card while armed

1. If the bench card is a legal target (in `legalBenchIds`): execute swap.
   - `applySwap(lineup, pendingStarterId, benchId, playerMap)` returns a new `OptimisedLineup` with starters swapped, bench swapped, captain/VC recomputed (Pitfall 2), formation recomputed (Pitfall 3).
   - `setLineup(newLineup); setPendingStarterId(null)`.
   - Visual response: ring/tint clears, captain badge moves if necessary, formation in HeadlineRow updates, total xPts recomputes.
2. If the bench card is not a legal target: button is `disabled` so click does nothing. (Defence in depth: the handler also re-checks `isLegalSwap` and silently ignores illegal swaps.)

### Tap a starter while a different starter is armed (re-arm)

1. User clicks a starter that is NOT `pendingStarterId`.
2. Handler: `setPendingStarterId(id)` (replace the armed starter).
3. Visual response: previous armed card returns to default; new armed card flips to amber. Legal-target set is recomputed for the new starter.

### Tap the same armed starter again (cancel)

1. User clicks the armed starter.
2. Handler: `pendingStarterId === id` → `setPendingStarterId(null)`.
3. Visual response: amber tint and ring clear; bench rings/dimming clear.

### Tap the pitch background (cancel)

1. User clicks anywhere inside the pitch container that is NOT a card (e.g. between rows, on the position label column).
2. Pitch container's `onClick` fires → `setPendingStarterId(null)`.
3. Visual response: armed/legal/incompatible visuals all clear.
4. **Required:** every card stops propagation (`e.stopPropagation()` in `onClick`). Without this, every card click ALSO triggers the background handler, immediately disarming the state (Pitfall 7).

### Tap Reset

1. User clicks Reset.
2. Reset handler: `setPendingStarterId(null); setLineup(initialLineup)`.
3. Visual response: any swaps revert; if a swap was armed, it cancels.
4. Reset button state: idle at all times (no loading state — synchronous).

### Outside-click on body (NOT pitch)

NOT implemented. Clicking on the page header, sub-tab nav, etc. does NOT clear `pendingStarterId`. The state clears only on:
- Tap the armed starter again, OR
- Tap the pitch background, OR
- Tap a legal bench target (swap fires + clears), OR
- Tap Reset.

This matches the explicit-interaction philosophy of Phases 58/59/60 — no auto-dismiss timers, no global click handlers.

### Data refetch behaviour

When TanStack Query refetches `usePlayers()` or `useSquad()` (e.g. after a stale-time window): the memoised `initialLineup` recomputes; the `useEffect` sync sets `lineup = initialLineup`; user overrides are wiped. This is documented in `072-RESEARCH.md` Pitfall 6 as accepted session-only behaviour per D-08. The footnote already implies session-only by saying "Reset restores the recommendation" — it does not promise persistence.

## States Required

### `LineupTab`

| State | Trigger | UI Response |
|-------|---------|-------------|
| Initial — no team ID submitted | `submittedId === null` | Heading + empty-state copy. No pitch, no Reset, no headline. |
| Loading — squad or players fetching | `isLoading === true` | Heading + `Loading squad...` text. No pitch, no Reset, no headline. |
| Error — squad fetch failed | `squadError !== null` | Heading + red error banner. No pitch, no Reset, no headline. |
| BGW critical — `< 11` eligible | `lineup === null && eligibleCount < 11` | Heading + amber `bgw-banner-critical`. No pitch, no Reset, no headline. |
| Engine returned null but `>= 11` eligible (defensive) | `lineup === null && eligibleCount >= 11` | Heading + red error banner with copy `Unable to optimise lineup. Please try again.`. No pitch. |
| BGW soft — `>= 11` eligible but `< 15` | `lineup !== null && eligibleCount < total` | Heading + Reset (top-right) + amber `bgw-banner-soft` + headline + pitch + footnote. |
| Lineup rendered — recommendation active | `lineup === initialLineup` (referential equality) | Heading + Reset (top-right) + headline + pitch + footnote. Reset button is inert if hovered (no-op when nothing is overridden) but always rendered. |
| Lineup rendered — user overridden | `lineup !== initialLineup` | Identical render to recommendation-active state — there is no visible "override" indicator on the headline. The user can confirm their swap took effect by reading the pitch. |

### Player card

| State | Trigger | UI Response |
|-------|---------|-------------|
| Default | `pendingStarterId === null` OR (`pendingStarterId !== null` AND card is in same row as armed starter and is NOT the armed starter) | `bg-zinc-50 dark:bg-zinc-800` border default + hover lift `hover:bg-zinc-100 dark:hover:bg-zinc-700`. |
| Armed (this card is the armed starter) | `id === pendingStarterId` | Amber tint + amber ring + amber border. `cursor-pointer` (re-tap to disarm). |
| Legal swap target (bench card during pending swap) | `isBench && legalBenchIds?.has(id)` | Standard zinc tint + green ring + green border (border colour change is implicit via `border-zinc-200`/dark variant — the ring is the dominant signal). `cursor-pointer`. |
| Incompatible (bench card during pending swap) | `isBench && legalBenchIds !== null && !legalBenchIds.has(id)` | `opacity-40 cursor-not-allowed`. Card is `disabled` (no focus, no click). |
| Captain | `id === captainId` | `C` badge top-right (amber-600 bold). |
| Vice-captain | `id === vcId` | `VC` badge top-right (zinc-500 semibold). |

### Reset button

| State | Trigger | UI Response |
|-------|---------|-------------|
| Always visible when pitch renders | `lineup !== null` | Solid zinc-inverse button reading `Reset`. |
| Hover | mouse over | `hover:bg-zinc-800 dark:hover:bg-zinc-200`. |
| Inert when nothing to reset | `lineup === initialLineup` | Same render — clicking is a no-op (state already equals initial). NOT visually disabled because `lineup === initialLineup` is fragile (refetch may have just invalidated overrides without UI feedback) — keeping the button always-active gives the user a reliable escape hatch. |

| State | Trigger | UI Response |
|-------|---------|-------------|
| Idle | `pendingStarterId === null` | All cards in default state. |
| Pending swap | `pendingStarterId !== null` | One armed card (amber); 0–4 bench cards green-ringed (legal); remaining bench cards dimmed. XI cards in OTHER rows render in default state — they are NOT swap targets. |

### Headline row

| State | Trigger | UI Response |
|-------|---------|-------------|
| Always visible when pitch renders | `lineup !== null` | `Formation: {f} │ Captain: {name} │ Total xPts: {N.N}`. Updates automatically after every swap because `lineup.formation`, `lineup.captainId`, and `totalXPts` are all derived from the held `lineup` state. |
