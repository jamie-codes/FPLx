**D-07/D-08 contradiction resolution (RESEARCH.md Open Question 1, Pitfall 4, A2; UI-SPEC.md §Reused Components):**

CONTEXT.md D-07 says horizon is "shared with section-level HorizonSelector in page.tsx" and UI-SPEC.md §Reused Components says "Route Tree does NOT render its own HorizonSelector". However, page.tsx today does NOT have a section-level HorizonSelector — both PlannerTab and ManualPlanTab render their own local HorizonSelector inside the tab body (verified at PlannerTab.tsx:341 and ManualPlanTab.tsx:327).

**Decision:** RouteTreeTab renders its OWN HorizonSelector inside the tab body, matching PlannerTab and ManualPlanTab. This is the path of zero regression risk: it does NOT touch sibling Plan sub-tabs, it does NOT modify page.tsx structure beyond the standard SubTab insert, and TRT-07 ("recalculates when horizon changes") is fully satisfied because `useMemo` keys on the local horizon state. UI-SPEC.md §Reused Components is OVERRIDDEN by this decision (logged in summary); a future phase may lift horizon to page.tsx if user demands cross-tab horizon sync — that is an enhancement, not a regression. Document this deviation in `060-02-SUMMARY.md`.

**chipMode (Pitfall 5, A3, TRT-06):** RouteTreeTab passes `chipMode: null` to the engine (constant — no UI ChipToggle in this tab per UI-SPEC §Reused Components). TRT-06 is satisfied at the engine level (Plan 01 Tests E1–E4); UI exposure is deferred per RESEARCH.md A3.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| RouteTreeTab → localStorage | RouteTreeTab writes a `ManualPlan` to `fplx_manual_plan` via `persistManualPlan` (D-08, D-09). Adversary can tamper with the localStorage value externally. |
| RouteTreeTab ← localStorage | RouteTreeTab reads existing manual plan via `loadManualPlan` to decide whether to show the inline confirm. The reader is responsible for shape validation. |
| client → RouteTreeTab | Squad picks come from `useMyTeam` (auth path) or `useSquad` (public path) — both validated upstream by zod schemas in squad-adapter.ts. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-60-02-01 | Tampering | `fplx_manual_plan` localStorage on bridge write | mitigate | `persistManualPlan` is the established write path. Any adversary-controlled localStorage payload is re-validated on the next mount of `ManualPlanTab` via `loadManualPlan`'s shape validation (manual-plan.ts:230–254 — version, horizon range, chip enum). RouteTreeTab does NOT re-implement persistence. |
| T-60-02-02 | Tampering | `fplx_manual_plan` localStorage on bridge read | mitigate | `loadManualPlan` returns null on invalid shape (manual-plan.ts:230–254). RouteTreeTab's `handleClickLoad` defensively uses `existing?.steps.some(...) ?? false` so a null/invalid existing plan is treated as "empty" and overwritten silently. Inline confirm fires ONLY when the existing plan is shape-valid AND has at least one transfer. |
| T-60-02-03 | Information Disclosure | RouteTreeTab DOM | accept | DOM contains only public/already-fetched FPL data (player names, prices). No PII, no secrets. Same disclosure profile as Phase 59 ManualPlanTab. |
| T-60-02-04 | Spoofing | onSwitchSubTab callback | accept | Callback is owned by `page.tsx` parent and passed as a prop — no cross-origin or cross-context risk. |
