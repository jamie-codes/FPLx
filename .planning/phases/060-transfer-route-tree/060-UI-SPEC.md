# Phase 60 — UI Design Contract: Transfer Route Tree

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This phase carries forward the design system established in `058-UI-SPEC.md` and `059-UI-SPEC.md` unchanged. Every spacing, typography, and color decision below mirrors Phase 58/59. New visual surfaces (route summary table, expandable GW breakdown row, Load-into-Manual-Planner inline confirm) are specified explicitly; reused components (`HorizonSelector`, `ChipToggle`, page-level Plan section header controls) are referenced by name only — their internals are NOT re-specified.

Exceptions (carried forward from Phases 58/59):

- **Touch targets:** `min-h-[44px]` on buttons inside the Route Tree (Load into Manual Planner, Expand path, Inline confirm). (Phase 59 spec also notes 48px is acceptable per Phase 58 — Phase 60 uses 44px to match Phase 59 sibling buttons inside the Plan section.)
- **Table cells:** `px-3 py-2` (12px / 8px) for summary table data cells; `px-3 py-3` (12px / 12px) for the table header row. Matches `TransferPlanTable` cell padding pattern.
- **Expanded breakdown row inner padding:** `px-3 py-3` (12px / 12px) — the breakdown is a `<tr>` with a `<td colSpan>` containing nested layout; outer padding lives on the inner content wrapper.
- **Inline confirm spacing:** the "Are you sure?" confirm state preserves the same `min-h-[44px] px-3 py-2` button geometry as the Load into Manual Planner default state — no layout shift on click.

Source: `058-UI-SPEC.md` Spacing Scale; `059-UI-SPEC.md` Spacing Scale; `src/components/planner/TransferPlanTable.tsx`; `src/components/planner/ManualPlanTab.tsx`.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#ffffff` / `#0a0a0a` | Page background (`bg-white dark:bg-zinc-900`), summary table base surface |
| Secondary (30%) | `zinc-50` / `zinc-800` | Table header band, expanded GW-by-GW breakdown row body, hover background |
| Accent (10%) | `green-700` / `green-300` ring + `zinc-900` / `zinc-100` button | Recommended-path ring highlight; "Load into Manual Planner" primary button (per-row) |
| Destructive | `red-700` / `red-300` text | Hit cost text when `totalHitCost > 0`; inline confirm "Cancel" affordance text only |

Accent reserved for (explicit list):

1. **Recommended-path ring** — the highest net-xPts row gets `ring-2 ring-offset-1 ring-green-700 dark:ring-green-300` applied to the row's outer container. This pattern is **already established** in the codebase: `ChipStrategyPanel.tsx` line 56 (`isBest` cell) and `DecisionSummaryTab.tsx` line 108 (recommended chip). Reusing it preserves visual continuity. The ring is applied via the row-level wrapper because `<tr>` ring offsets don't render reliably across browsers — the engine renders each path as a `<div>` "row" inside an outer card OR uses `ring-inset` on `<tr>`. (Implementation detail: see Component Inventory §Layout choice.)
2. **Recommended-path badge** ("Recommended"): `bg-green-100 text-green-700 dark:bg-green-900 dark:text-green-300 text-xs font-semibold rounded px-2 py-1`. Sits inline next to the path label in the recommended row.
3. **"Load into Manual Planner" button** (per-row, default state): `bg-zinc-900 dark:bg-zinc-100 text-white dark:text-zinc-900 font-semibold rounded min-h-[44px] px-3 py-2 text-sm hover:bg-zinc-800 dark:hover:bg-zinc-200 cursor-pointer`. Same zinc-inverse pattern as the Phase 59 "Load Squad" button and Phase 58 "Load Rivals" button.
4. **Active state of `HorizonSelector` segments** (1 / 3 / 5 GW) — inherited from reused component at the Plan section header level (D-07). Route Tree does NOT render its own HorizonSelector.

Accent is NOT used for: expand/collapse chevron, table column headers, neutral metrics, the "Cancel" affordance during inline confirm. These use neutral text colors.

Semantic badge / status colors (status indicators, NOT accent — carried forward from Phases 58/59):

- **Recommended badge:** `bg-green-100 text-green-700 dark:bg-green-900 dark:text-green-300` (see above).
- **Hit cost negative value** (when `totalHitCost > 0`): `text-red-700 dark:text-red-300 font-semibold`. When `totalHitCost === 0`, render plain `text-zinc-900 dark:text-zinc-100` with the literal `0 pts`.
- **Chips preserved indicator** (when path consumes 0 chips): `text-zinc-500 dark:text-zinc-400` plain text reading `All preserved`.
- **Chips consumed indicator** (when path uses a chip): inline pill `bg-amber-100 text-amber-800 dark:bg-amber-900 dark:text-amber-200 text-xs font-semibold rounded px-2 py-1` with the chip code (`WC`, `FH`, `BB`, `TC`).

Borders: `border-zinc-200 dark:border-zinc-700` (table outer wrapper, summary card); `border-zinc-100 dark:border-zinc-700` (inner row dividers, expanded breakdown top border).

Dark-mode surface pattern (project standard):

## Component Inventory

### Visual Hierarchy (Focal Point)

- **No-squad state:** Single Team ID input + "Load Squad" CTA centered in the tab body. The empty state heading + body copy is the only other content. The submit button is the visual anchor (mirrors Phase 59 D-09 pattern).
- **Loading state (squad loaded, tree computing):** brief inline `Computing routes…` text replacing the table region. `useMemo` is synchronous so this rarely renders for more than one frame; the state exists primarily for type safety on initial mount before `picks` resolves.
- **Routes-rendered state (typical):** The summary table is the primary visual anchor. The recommended-path row carries the green ring + "Recommended" badge — the eye lands there first. The expand toggle on each row is the secondary affordance; "Load into Manual Planner" is the per-row CTA.
- **Empty-tree state (squad loaded but engine returned 0 paths — defensive case):** brief explanatory message: "No transfer routes found for the current horizon and chip mode. Try a different horizon or clear the active chip." No table rendered.

### Layout choice — table vs cards

The summary view is **a single `<table>` with `overflow-x-auto` wrapping** (matching `TransferPlanTable` and Phase 59 D-10). The recommended-path highlight uses a CSS pattern that works on `<tr>`:

```
<tr className={isRecommended
  ? 'ring-2 ring-offset-0 ring-inset ring-green-700 dark:ring-green-300 bg-zinc-50 dark:bg-zinc-800'
  : 'hover:bg-zinc-50 dark:hover:bg-zinc-800/50'}>
```

`ring-inset` is required because outset rings on `<tr>` are clipped by the table layout in some browsers; inset rings render reliably. This is the only deviation from the `ChipStrategyPanel`/`DecisionSummaryTab` outset-ring pattern and is forced by the `<tr>` substrate. The `bg-zinc-50 dark:bg-zinc-800` background on the recommended row also subtly tints the row to disambiguate from hover.

### New Components

#### `RouteTreeTab.tsx` — `src/components/planner/`

The entry-point container. Owns local UI state (`expandedPaths: Set<number>`, `confirmingLoadIndex: number | null`), reads squad/auth/players from hooks, calls the pure engine `buildTransferRouteTree(...)` from `src/lib/transfer-route-tree.ts`, and renders the summary table.

Top-level structure:

```
<section> RouteTreeTab (root)
├── No-squad branch (mirror Phase 59 D-09):
│   ├── Heading "Route Tree" + sub-heading
│   ├── Empty-state copy block ("Load your squad first")
│   └── Team ID input + Load Squad button
└── Squad-loaded branch:
    ├── Heading row: "Route Tree" + one-sentence description
    ├── (Optional) Caveat banner — inherited from Phase 59 pattern, shown only when unauthenticated
    ├── Routes summary table (overflow-x-auto wrapper)
    │   ├── <thead>: Path | Hits | Hit cost | Net xPts | Chips | Action
    │   └── <tbody>: For each path in tree.paths:
    │       ├── Summary <tr> (data row)
    │       └── Expanded breakdown <tr> (only if expandedPaths.has(i)) — single <td colSpan={6}>
    └── Empty-tree fallback (rendered instead of table when paths.length === 0)
```

#### `RouteSummaryTable.tsx` (or inline within RouteTreeTab)

A presentational sub-component (executor's choice — may be inlined since it is used only here). Renders the summary table with columns:

| Column | Header label | Body cell |
|--------|--------------|-----------|
| 1 | `Path` | `Path A` / `Path B` / `Path C` + (if recommended) `Recommended` badge inline-block to the right |
| 2 | `Hits` | Integer count of hit transfers across the path |
| 3 | `Hit cost` | `0 pts` (zinc) or `−{N} pts` (red, `font-semibold`) using minus sign U+2212 |
| 4 | `Net xPts` | One decimal `+{X.X}` or `{X.X}` (signed display); positive values always carry leading `+` |
| 5 | `Chips` | `All preserved` (muted text) OR amber pill containing chip codes consumed (`WC`, `FH`, `BB`, `TC`) — comma-separated if multiple. Never both. |
| 6 | `Action` | "Load into Manual Planner" button (default) OR "Are you sure?" / "Cancel" pair (confirm state) |

A small expand chevron sits at the start of each summary row (column-1 prefix), styled `text-zinc-500 dark:text-zinc-400 text-xs hover:text-zinc-700 dark:hover:text-zinc-200`. Chevron text: `▼` (closed) / `▲` (open). Clicking the chevron toggles expandedPaths for that index.

Row click target: ONLY the chevron toggles expand (NOT the entire row, to avoid accidental expansion when the user means to click "Load into Manual Planner").

#### Expanded GW-by-GW breakdown row

When a path is expanded, an immediately following `<tr>` is rendered:

```
<tr>
  <td colSpan={6} className="bg-zinc-50 dark:bg-zinc-800 border-t border-zinc-100 dark:border-zinc-700 px-3 py-3">
    <div className="overflow-x-auto">
      <table className="text-xs w-full">
        <thead>
          <tr className="text-zinc-500 dark:text-zinc-400">
            <th>GW</th><th>Sell</th><th>Buy</th><th>FT bank</th><th>Free / Hit</th><th>xPts contribution</th>
          </tr>
        </thead>
        <tbody>
          {/* one <tr> per node in path.nodes */}
        </tbody>
      </table>
    </div>
  </td>
</tr>
```

Per-step row content:

- **GW:** integer GW number, plain text.
- **Sell:** outgoing player `web_name` (font-medium) OR em-dash `—` (when step is a hold).
- **Buy:** incoming player `web_name` (font-medium) OR em-dash `—` (when step is a hold).
- **FT bank:** integer FT count after the step (`1`, `2`).
- **Free / Hit:** small inline badge — `Free` (green-100/green-700) when `hitCost === 0`, `Hit −4 pts` (red-100/red-700) when `hitCost === 4`, em-dash when step is a hold. Badges reuse the exact classes from Phase 59 `TransferRow`.
- **xPts contribution:** `+{X.X}` (signed). Use `text-zinc-900 dark:text-zinc-100` plain (NOT colored) — color is reserved for hit cost in the summary row.

#### "Load into Manual Planner" button — three states

State 1 — default:

```
<button onClick={handleClickLoad}
        className="bg-zinc-900 dark:bg-zinc-100 text-white dark:text-zinc-900

                   hover:bg-zinc-800 dark:hover:bg-zinc-200 cursor-pointer
                   whitespace-nowrap">
  Load into Manual Planner
</button>
```

State 2 — inline confirm (D-08, only triggered when `loadManualPlan()` returns a non-empty plan):

```
<div className="flex items-center gap-2">
  <span className="text-sm text-zinc-700 dark:text-zinc-300 whitespace-nowrap">
    Replace current plan?
  </span>
  <button onClick={handleConfirmLoad}
          className="bg-zinc-900 dark:bg-zinc-100 text-white dark:text-zinc-900
                     font-semibold rounded min-h-[44px] px-3 py-2 text-sm cursor-pointer">

  </button>
  <button onClick={handleCancelLoad}
          className="text-sm text-zinc-500 dark:text-zinc-400 hover:text-zinc-700

```

The inline confirm replaces the button in-place — no popover, no modal. This matches CONTEXT specifics §3 "not a modal, just an inline confirmation state". Layout shift is unavoidable when the confirm spreads (3 elements vs 1) — the table's `overflow-x-auto` accommodates this.

```
</span>
```

This state may be skipped entirely if the sub-tab switch happens synchronously inside the click handler. If the executor implements the switch via `setActiveSubTab('manual-plan')` immediately after `persistManualPlan(...)`, State 3 never renders — that is acceptable.

```
<div className="rounded border border-zinc-200 dark:border-zinc-700
                bg-zinc-50 dark:bg-zinc-800 px-4 py-6 text-center">
  <p className="text-sm text-zinc-700 dark:text-zinc-300">
    No transfer routes found for the current horizon and chip mode.

  <p className="text-xs text-zinc-500 dark:text-zinc-400 mt-1">
```

#### Mobile element-hiding strategy

The `overflow-x-auto` wrapper preserves all 6 columns on mobile (per D-10 — users swipe horizontally rather than columns being hidden). This matches Phase 59 D-10. No columns are conditionally hidden by breakpoint.

The expanded breakdown's nested `<table>` ALSO scrolls horizontally inside its own `overflow-x-auto` wrapper so the breakdown does not force the parent table wider than the viewport.

The "Load into Manual Planner" button label uses `whitespace-nowrap` to avoid wrapping mid-label; the column accommodates via outer scroll.

## Interaction Contracts

### Tab activation

1. User clicks "Route Tree" sub-tab in the Plan section nav (or "Routes" on mobile).
2. `activeSection === 'plan' && activeSubTab === 'route-tree'` evaluates true.
3. `RouteTreeTab` mounts; reads `picks`, `playerMap`, `horizon`, `chipMode`, `initialFTState`, `bankBalance` from props supplied by `page.tsx`.
4. If `picks` is null → render no-squad branch. Else → call `buildTransferRouteTree({...})` inside `useMemo` and render the summary table.

### Squad loading branch (D-09 mirror)

1. On mount, hooks fire (read from same hooks Phase 59 already uses): `useAuthStatus`, `usePlayers`, `useSquad(teamId)`, `useMyTeam(isAuthenticated)`.
2. `picks = myTeamData?.picks ?? squadData?.picks ?? null`.
3. **No `picks`:** render the no-squad empty state. The summary table is NOT rendered. No tree computation occurs (early return before the `useMemo`).
4. **`picks` available:** render the full table UI. If `!isAuthenticated` AND `picks` is from public `useSquad` → show caveat banner above the table identical to Phase 59 (sell prices approximate copy).

### Horizon change (D-07 — automatic recomputation)

1. User toggles `HorizonSelector` at the Plan section header.
2. `horizon` prop on `RouteTreeTab` updates.
3. The `useMemo` on `buildTransferRouteTree({..., horizon})` recomputes synchronously.
4. Summary table re-renders with new path metrics.
5. Expanded paths (`expandedPaths` set) are CLEARED on horizon change — paths from a 5-GW tree don't map cleanly to a 3-GW tree, so the expand state is invalidated.
6. NO localStorage persistence of expand state — session-only.

### Chip change (D-08 — TRT-06 compliance)

1. User changes `chipMode` (Wildcard / Free Hit / Bench Boost / none) at the Plan section header.
2. `chipMode` prop on `RouteTreeTab` updates.
3. `useMemo` recomputes — engine respects chip rules (e.g., Wildcard removes hit costs for that GW; Free Hit is a one-GW reset that auto-reverts).
4. Summary metrics update; recommended-path designation may shift to a different row.
5. Expanded paths are NOT cleared — chip change keeps step structure (still N steps), only metrics shift.

### Expand path

1. User clicks the chevron `▼` in the path's leftmost column.
2. `setExpandedPaths(prev => { const next = new Set(prev); next.has(i) ? next.delete(i) : next.add(i); return next; })`.
3. The expanded `<tr>` mounts immediately below the summary row with the GW-by-GW breakdown.
4. Chevron flips to `▲`.
5. Clicking again closes.
6. Multiple paths can be expanded simultaneously. No mutual exclusion.

### Load into Manual Planner (D-08, TRT-05)

1. User clicks "Load into Manual Planner" on path `i`'s row.
2. Component reads `loadManualPlan()` from `src/lib/manual-plan.ts` — synchronous localStorage read.
3. **If returned plan has any step with `transfersIn.length > 0`:** set `confirmingLoadIndex = i`. Button replaces in-place with the inline confirm state (Replace current plan? + Yes, replace + Cancel).
4. **If returned plan is empty / null:** skip confirm; jump directly to step 6 (silent overwrite per D-08).
5. On "Yes, replace" click OR cancel:
   - Cancel: `setConfirmingLoadIndex(null)` — return to default button state.
   - Confirm: proceed to step 6.
6. Build bridge payload (D-09):
   - `horizon` = current Route Tree horizon.
   - `steps[i]` = `{ gw: path.nodes[i].gw, transfersIn: [path.nodes[i].buyId], transfersOut: [path.nodes[i].sellId], chip: 'none' }` for each transfer-bearing node. Hold-only nodes contribute `{ gw, transfersIn: [], transfersOut: [], chip: 'none' }`.
7. Call `persistManualPlan({ horizon, steps, version: 1 })`.
8. Call the prop callback `onSwitchSubTab('manual-plan')` — `RouteTreeTab` does NOT directly mutate URL or page state. Parent (`page.tsx`) owns `activeSubTab` setter.
9. `confirmingLoadIndex` resets to `null` on unmount.

### Outside-click behavior on inline confirm

Not implemented in v1 — the confirm persists on the row until the user explicitly clicks Cancel or Yes, replace. This matches Phase 59's preference for explicit interactions (no auto-dismiss timers) and avoids ambiguity if the user clicks another row's expand chevron.

- **Caveat banner amber, NOT red** — informational, not error (Phase 59 spec §Color).
- **"Recommended" (capitalised, single word)** — matches the project's badge convention; no "Best path" or "Top route" alternatives.
- **"Load into Manual Planner" (full phrase)** — explicit destination + verb. NOT "Open in Planner" / "Edit". The destination is the Manual Plan sub-tab specifically — vague language would mislead.
- **"Replace current plan?" (D-08 wording)** — derived from CONTEXT.md specifics §"This will replace your current manual plan. Continue?" but condensed to fit the inline confirm space without changing meaning. The `Yes, replace` confirm verb mirrors `Replace`.
- **"All preserved"** chip status — short, scan-friendly. NOT "0 chips used" / "No chips consumed".
- **"Path A / Path B / Path C"** — letters, not numbers. Avoids confusion with "Path 1" suggesting hierarchy when paths are alternatives, not steps. Phase 50 OCSTable uses similar lettered/named row labels.

## States Required

### `RouteTreeTab`

| State | Trigger | UI Response |
|-------|---------|-------------|
| Initial — no squad, no Team ID submitted | First visit, no `submittedId` | Empty-state heading + body + Team ID input + Load Squad button. No table. No tree computation. |

| Tree returned 1–3 paths | `tree.paths.length >= 1` | Summary table with N rows; row with highest `netXpts` carries Recommended badge + green inset ring. |

### "Load into Manual Planner" button

| State | Trigger | UI Response |
|-------|---------|-------------|
| Default | `confirmingLoadIndex !== i` | Solid zinc-inverse button reading `Load into Manual Planner`. |

| Confirming (other row) | `confirmingLoadIndex !== null && confirmingLoadIndex !== i` | This row's button stays in default state. Only one row can be in confirm state at a time (state is a single index, not a Set). |
