- Touch targets: FT toggle buttons inherit the existing `GwToggle` minimum height (`min-h-[44px]` already applies to all toggle buttons in the project). New FT toggle MUST meet the same 44px minimum.

## Copywriting Contract

All visible copy strings for Phase 45. Strings carried from Phase 44 (panel heading, empty/loading/error states, BGW banner) are unchanged.

| Element | Copy |
|---------|------|
| **Section header** | `Transfer Suggestions` |
| **FT toggle label** | `Free transfers:` |
| **FT toggle button — 1 FT** | `1 FT` |
| **FT toggle button — 2 FTs** | `2 FTs` |
| **Suggestion row format (single line — FREE)** | `Out: {sellName} → In: {buyName} │ FREE │ +{X.X} xPts` |
| **Suggestion row format (single line — -4pt hit)** | `Out: {sellName} → In: {buyName} │ -4pts │ +{X.X} xPts` |
| **Suggestion row — break-even subline (hit only)** | `Breaks even in {N} GW` (singular) / `Breaks even in {N} GWs` (plural — N >= 2 or N === 0) |
| **Suggestion row — break-even unreachable** | `Hit not recovered within horizon` (when `xPtsGainPerGw <= 0` — defensive; should be filtered out by engine but UI must not crash) |
| **Cost pill — no hit** | `FREE` |
| **Cost pill — hit** | `-4pts` |
| **xPts gain prefix** | `+` (always, since suggestions with non-positive net gain are filtered out by the engine) |
| **xPts gain format** | `{X.X}` (1 decimal, e.g. `+1.8`, `+0.4`) |
| **xPts unit suffix** | ` xPts` (single space + "xPts" — same as Phase 44 delta pill) |
| **Out / In labels** | `Out:` and `In:` (with colon, capitalised — chosen over Sell/Buy because "Out/In" is the FPL UI's own vocabulary; matches `45-CONTEXT.md` D-07 specifics) |
| **Arrow separator** | `→` (U+2192, text character — matches Phase 44 arrow) |
| **Pipe separator** | `│` (U+2502 vertical line — matches Phase 44 headline-row pipe) |
| **Empty state — no improvements** | `Your current squad is already optimal for this horizon.` |
| **Empty state — engine running / loading** | re-uses existing `Loading squad...` (no separate transfer-loading state — suggestions appear instantly once `useMemo` recomputes) |
| **Pre-condition empty state — no team ID** | (no separate copy — the OptimiserPanel-level "Enter your FPL Team ID..." empty state already gates rendering of the transfer section. Transfer section is only rendered when `lineup !== null`.) |

**No destructive actions in this phase.** Suggestions are read-only — the user does not commit transfers from this UI (FPL transfers must be made on the official FPL site, per project decision; this is purely advisory).

**No tooltip / help copy.** The FT toggle is self-explanatory ("Free transfers: [1 FT] [2 FTs]"). The break-even copy ("Breaks even in X GWs") is the literal TFR-03 requirement string and needs no further explanation.

**Plurality rules:**
- Break-even: `1 GW` (singular when N=1), `0 GWs` and `2+ GWs` (plural otherwise). Note: `0 GWs` only appears when the engine filters fail; defensive copy.
- xPts gain: always `xPts` (no singular form — "xPt" is never used in the codebase).

### 1. FT Toggle Component (D-01, D-02)

**Source:** D-01, D-02 from 45-CONTEXT.md.

A two-button pill toggle that mirrors the existing `GwToggle` visual identity (same shape, same active/inactive treatment, same touch-target height).

**File:** `src/components/optimiser/FtToggle.tsx` (new component)

**Visual structure:**
```
<div className="flex items-center gap-2" data-testid="ft-toggle">
  <span className="text-xs text-zinc-500 dark:text-zinc-400">Free transfers:</span>
  <div className="inline-flex rounded-md overflow-hidden border border-zinc-200 dark:border-zinc-700">
    <button
      type="button"
      onClick={() => onChange(1)}
      aria-pressed={value === 1}
      className={
        `min-h-[44px] px-3 text-xs font-semibold transition-colors ` +
        (value === 1
          ? 'bg-zinc-900 dark:bg-white text-white dark:text-zinc-900'
          : 'bg-zinc-100 dark:bg-zinc-800 text-zinc-700 dark:text-zinc-300 hover:bg-zinc-200 dark:hover:bg-zinc-700')
      }
      data-testid="ft-toggle-1"
    >
      1 FT
    </button>
    <button
      type="button"
      onClick={() => onChange(2)}
      aria-pressed={value === 2}
      className={
        `min-h-[44px] px-3 text-xs font-semibold transition-colors ` +
        (value === 2
          ? 'bg-zinc-900 dark:bg-white text-white dark:text-zinc-900'
          : 'bg-zinc-100 dark:bg-zinc-800 text-zinc-700 dark:text-zinc-300 hover:bg-zinc-200 dark:hover:bg-zinc-700')
      }
      data-testid="ft-toggle-2"
    >
      2 FTs
    </button>
  </div>
</div>
```

**Props:**
```ts
interface FtToggleProps {
  value: 1 | 2
  onChange: (value: 1 | 2) => void
}
```

**Default:** `value = 1` (D-02 — most common scenario).

**Placement:** sits at the top of the Transfer Suggestions section, immediately under the section header (NOT inline with the horizon selector — see §6 for layout). This avoids visual collision with the horizon toggle that sits above the comparison table.

**Accessibility:**
- Both buttons are `<button type="button">` (avoids form submission inside any wrapping form).
- `aria-pressed` reflects the active state.
- Minimum 44px touch target (matches `GwToggle.tsx` pattern).
- Buttons are inside an `inline-flex` container with the rounded-corner border on the wrapper, not on individual buttons (avoids double borders between adjacent buttons).

### 5. Two-Transfer Combo Layout (D-04)

**Source:** D-04 (engine enumerates 2-FT pairs); UI must render the pair as a logical unit.

When `ftCount = 2` and the engine returns a 2-transfer suggestion, both transfers belong to a single recommendation. They are rendered as a SINGLE card with a sub-divider:

**Variant C — 2-transfer combo row:**
```
<div
  className="border-b border-zinc-100 dark:border-zinc-800 py-2 px-2 bg-zinc-50/50 dark:bg-zinc-800/30 rounded"
  data-testid="suggestion-row"
  data-variant="combo"
>
  {/* Transfer 1 */}
  <div className="flex flex-wrap items-center gap-x-2 gap-y-1 text-sm">
    <span className="text-zinc-500 dark:text-zinc-400">Out:</span>
    <span className="font-medium text-zinc-700 dark:text-zinc-300">{sell1.web_name}</span>
    <span className="text-zinc-400 dark:text-zinc-500">→</span>
    <span className="text-zinc-500 dark:text-zinc-400">In:</span>
    <span className="font-medium text-green-700 dark:text-green-400">{buy1.web_name}</span>
  </div>
  {/* Transfer 2 */}
  <div className="flex flex-wrap items-center gap-x-2 gap-y-1 text-sm mt-0.5">
    <span className="text-zinc-500 dark:text-zinc-400">Out:</span>
    <span className="font-medium text-zinc-700 dark:text-zinc-300">{sell2.web_name}</span>
    <span className="text-zinc-400 dark:text-zinc-500">→</span>
    <span className="text-zinc-500 dark:text-zinc-400">In:</span>
    <span className="font-medium text-green-700 dark:text-green-400">{buy2.web_name}</span>
  </div>
  {/* Aggregate cost / gain row */}
  <div className="flex flex-wrap items-center gap-x-2 gap-y-1 text-sm mt-1 pt-1 border-t border-zinc-200 dark:border-zinc-700">
    {/* Cost pill: FREE if total transfers <= ftCount, otherwise -4pts × hits */}
    <span
      className={
        isFree
          ? 'text-xs font-semibold text-green-400 bg-green-950 rounded px-1 py-0.5'
          : 'text-xs font-semibold text-amber-800 dark:text-amber-200 bg-amber-50 dark:bg-amber-950 border border-amber-400 rounded px-1 py-0.5'
      }
      data-testid={isFree ? 'cost-pill-free' : 'cost-pill-hit'}
    >
      {isFree ? 'FREE' : `-${4 * hitCount}pts`}
    </span>
    <span className="text-zinc-400 dark:text-zinc-500">│</span>
    <span className="font-semibold text-green-600 dark:text-green-400">+{xPtsGain.toFixed(1)} xPts</span>
  </div>
  {/* Break-even subline (only shown when at least one hit is involved) */}
  {!isFree && (
    <div
      className="text-xs text-zinc-500 dark:text-zinc-400 mt-0.5"
      data-testid="break-even"
    >
      Breaks even in {breakEvenGws} {breakEvenGws === 1 ? 'GW' : 'GWs'}
    </div>
  )}
</div>
```

**Cost pill copy in combo:**
- 2 transfers, ftCount=2 → `FREE`
- 2 transfers, ftCount=1 → `-4pts` (one hit)
- 1 transfer, ftCount=1 → uses Variant A (FREE) — engine returns single-transfer in this case
- 1 transfer, ftCount=2 → uses Variant A (FREE, banking the second FT)

**Visual distinction from single-transfer cards:** combo cards use `bg-zinc-50/50 dark:bg-zinc-800/30` background tint and an internal `border-t` divider before the cost row. This differentiates "this is one decision with two moves" from two separate decisions.

### 6. Mobile Layout (CMP-03 inheritance — same responsive approach)

**Source:** Phase 44 mobile responsive pattern (D-09 from Phase 44).

The transfer suggestion section uses the SAME responsive breakpoint as the comparison table (`< sm` → 640px). However, because suggestion rows already use `flex-wrap`, the desktop layout naturally adapts to narrow viewports without a separate mobile structure.

**Specific mobile adjustments:**
- The FT toggle remains visible on mobile — placed below the section header, above the suggestion list. Same desktop component, no mobile-only variant.
- Suggestion rows wrap their content via `flex-wrap` — on a 360px viewport, the row may wrap to 2-3 visual lines (Out/In on one line, cost+gain on the next). This is acceptable and matches the Phase 44 headline-row mobile behaviour.
- The break-even subline's `ml-[3.25rem]` indent is RESET on mobile to `ml-0` for readability:
  ```
  className="text-xs text-zinc-500 dark:text-zinc-400 mt-0.5 ml-0 sm:ml-[3.25rem]"
  ```
- Section header (`<h3>`) stays at `text-sm` on mobile (no responsive scale-down — already small enough).
- Empty state layout is unchanged on mobile (already fluid).

No separate `MobileSuggestionCards` component is needed. The responsive design is achieved via Tailwind utility classes on the same DOM, unlike Phase 44's table-vs-cards split.

### 9. Engine Output Shape (UI contract — informative only)

The UI consumes a `TransferSuggestion[]` array. Shape (locked at the UI/engine boundary so the executor cannot add/remove fields without a UI-SPEC change):

```ts
type TransferSuggestion =
  | {
      kind: 'single'
      sell: MergedPlayer
      buy: MergedPlayer
      cost: 0 | 4              // 0 = FREE, 4 = -4pt hit
      xPtsGain: number          // always > 0 (negative gains filtered by engine)
      xPtsGainPerGw: number     // for break-even calc; xPtsGain / horizon
      breakEvenGws: number | null  // ceil(4 / xPtsGainPerGw) when cost > 0; null when FREE
    }
  | {
      kind: 'combo'
      transfers: [{ sell: MergedPlayer; buy: MergedPlayer }, { sell: MergedPlayer; buy: MergedPlayer }]
      cost: 0 | 4              // 0 = FREE (both within ftCount), 4 = one hit
      xPtsGain: number
      xPtsGainPerGw: number
      breakEvenGws: number | null
    }
```

**Render-time invariants the UI relies on:**
- `xPtsGain > 0` for every suggestion (the engine MUST filter non-positive gains).
- `breakEvenGws === null` if and only if `cost === 0`.
- `breakEvenGws >= 1` when present (the engine MUST clamp to a minimum of 1 to avoid `Breaks even in 0 GWs` copy).
- All suggestions are budget-feasible (D-10 hard filter applied upstream).

If any invariant is violated at runtime, the UI falls back to the defensive copy `Hit not recovered within horizon` (defined in Copywriting Contract §). The UI never crashes on bad engine output.
