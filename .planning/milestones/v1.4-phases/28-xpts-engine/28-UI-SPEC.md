| Element | Light | Dark | Rationale |
|---------|-------|------|-----------|
| High-ceiling badge (⬆) background | violet-100 | violet-900 | Distinct from green/amber/red FixtureBadges tiers; matches existing `text-violet-700/violet-400` DGW prefix in `FixtureBadges.tsx` for "ceiling/upside" semantic |
| High-ceiling badge (⬆) text | violet-800 | violet-200 | Matches `MinsRiskBadge` text contrast pattern (`text-{color}-800 dark:text-{color}-200`) |
| Consistent badge (=) background | zinc-100 | zinc-700 | Neutral, low-emphasis — same envelope as the existing "Cameo" MinsRisk badge (lowest-emphasis surface) |
| Consistent badge (=) text | zinc-600 | zinc-300 | Matches "Cameo" badge text exactly — signals "informational, no recommended action" |

Accent (zinc-900/white) reserved for: active `GwToggle` pill background only. Variance badges do NOT use the accent color — they use violet (high-ceiling) and zinc (consistent) so they remain semantically distinct from interactive controls.

**Why violet for ⬆ (not amber/green/red):**
- Green is reserved for "easy fixture" tier (FixtureBadges) and "Nailed" minutes (MinsRiskBadge) — would collide
- Amber is reserved for "rotation risk" (MinsRiskBadge), "Changed" set-piece badge, and "medium fixture" tier (FixtureBadges) — would collide
- Red is reserved for "hard fixture" tier and error states — high-ceiling is positive (upside), not negative
- Violet is already the established "rare / structural-event" color in the codebase (DGW prefix in `FixtureBadges.tsx` line 24) — high-variance ceiling players are statistically rare relative to the consistent baseline, so the semantic carries

Source: codebase scan — `FixtureBadges.tsx` (DGW violet at line 24, tier colours), `MinsRiskBadge.tsx` (amber/green/blue/zinc envelopes), `GemTable.tsx` (row hover, header bg).

## Component Inventory

### 1. Renamed columns (xPts_1gw / xPts_3gw / xPts_5gw)

**Purpose**: D-02 — replace the three "Proj Pts" / "Proj Pts (3)" / "Proj Pts (5)" column definitions in `gem-table/columns.tsx` with xPts equivalents that read the new pipeline fields. Same column position, same `GwToggle` wiring, same DGW summing semantics.

**Structure (per column):**
```tsx
col.accessor('xPts_1gw', {
  header: H('xPts', '<header tooltip — see Copywriting Contract>'),
  cell: (info) => <XPtsCell row={info.row.original} window={1} />,
  enableSorting: true,
})
```

The cell renderer is a new tiny inline component (`<XPtsCell>`) that composes:
1. The numeric xPts value (`.toFixed(1)`)
2. A `<VarianceBadge>` (when `xPts_ceiling_<window>` is present) appended after the number
3. A native `title` tooltip on the wrapping `<span>` containing the component breakdown

**Cell DOM (target shape):**
```tsx
<span title={breakdownTooltip} className="cursor-help">
  {value.toFixed(1)}
  <VarianceBadge ceiling={row.xPts_ceiling_<window>} />
</span>
```

**`breakdownTooltip` content (multi-line, native `title`):**
```
xPts breakdown ({N} GW):
Goals: {goal_pts}
Assists: {assist_pts}
Clean sheet: {cs_pts}
Bonus: {bonus_pts}
```

Numbers in the tooltip use `.toFixed(2)` (one extra decimal of precision than the cell number) so the breakdown components visibly add up to the displayed cell number after rounding.

**`GwToggle` integration**: D-05 — `getColumnVisibility(horizon)` in `GwToggle.tsx` is updated to gate `xPts_1gw / xPts_3gw / xPts_5gw` (replaces the existing `proj_pts_1gw / proj_pts_3gw / proj_pts_5gw` keys 1:1). No new toggle state, no new component prop.

**Mobile column visibility**: All three xPts columns must NOT appear in `MOBILE_HIDDEN_COLUMNS` (matching existing `proj_pts_*gw` behaviour — these are the headline numeric columns and remain visible on mobile). Mobile expanded-row dictionary list (`HIDDEN_COLUMN_LABELS` in `GemTable.tsx`) requires no entry for xPts since the column itself stays visible.

**Sort behaviour**: `enableSorting: true` per column — TanStack handles numeric sort. Default sort (`gem_score desc`) is unchanged. Users sort by xPts via header click, same UX as proj_pts today.

**States:**
- **Has data**: number + variance badge + tooltip
- **Pipeline emitted `null` / `undefined`** (e.g. empty GW for a player with no fixture): render `0.0` with NO variance badge and NO breakdown tooltip — match existing `(info.getValue() ?? 0).toFixed(1)` pattern in current proj_pts columns
- **Pipeline emitted a positive number but `xPts_ceiling_<window>` is null/undefined**: render number with NO badge (still show breakdown tooltip if components are present) — graceful degrade for partial pipeline output

### 2. VarianceBadge

**Purpose**: D-07 — inline icon badge after the xPts number that signals "high-ceiling" or "consistent". Tooltip on hover/tap explains what it means in FPL terms.

**Structure:**
```tsx
function VarianceBadge({ ceiling }: { ceiling: boolean | undefined }) {
  if (ceiling === undefined) return null
  if (ceiling === true) {
    return (
      <span
        className="ml-1 inline-block text-xs font-normal rounded px-2 py-1 bg-violet-100 dark:bg-violet-900 text-violet-800 dark:text-violet-200"
        title="High ceiling: this player's points are highly variable (top-tercile σ across all players). Good captain pick when chasing rank in a mini-league."
      >
        ⬆
      </span>
    )
  }
  return (
    <span
      className="ml-1 inline-block text-xs font-normal rounded px-2 py-1 bg-zinc-100 dark:bg-zinc-700 text-zinc-600 dark:text-zinc-300"
      title="Consistent: this player's points are stable GW-to-GW (below top-tercile σ). Safe floor pick when protecting rank."
    >
      =
    </span>
  )
}
```

**Visibility rules:**
- Rendered only when `xPts_ceiling_<window>` is `true` or `false` (boolean precomputed in pipeline). When `undefined` / `null` → render nothing (no slot, no placeholder).
- Same component used for all three windows (1 GW, 3 GW, 5 GW) — the cell renderer reads the matching `xPts_ceiling_1gw` / `xPts_ceiling_3gw` / `xPts_ceiling_5gw` field per active GwToggle horizon.
- Non-interactive (no click, no expand). Tooltip is the only affordance.

**Pattern source**: Matches `MinsRiskBadge.tsx` envelope exactly (`inline-block text-xs font-normal rounded px-2 py-1` + `title` attribute + light/dark colour pair).

### 3. xPts breakdown tooltip (native `title` on cell)

**Purpose**: XPTS-01 component breakdown — surface goal pts / assist pts / CS pts / bonus pts on hover (desktop) or long-press (mobile, inherited browser behaviour) without adding columns or table width.

**Mechanism**: Wrap the cell number+badge in a single `<span title={multiline} className="cursor-help">` so the whole cell triggers the native browser tooltip. `cursor-help` matches the existing column-header tooltip pattern (`columns.tsx` line 17) so users get the same affordance signal.

**Tooltip text format** (literal, with `\n`):
```
xPts breakdown ({N} GW):
Goals: 1.42
Assists: 0.83
Clean sheet: 0.27
Bonus: 0.31
```

`{N}` = current `gwHorizon` (1 / 3 / 5). The breakdown row labels are sentence-case ("Clean sheet", not "Clean Sheet" or "CS").

**No tooltip when**:
- Components dict is `null` / `undefined` (pipeline didn't emit) — cell stays interactive but no `title` attribute
- All four component values are `0` simultaneously (BGW / no fixture) — render number `0.0` with NO tooltip and NO variance badge

**Why native `title` (not a custom Tooltip component):**
- Existing project pattern — every column header in `gem-table/columns.tsx`, `defcon/columns.tsx`, and every badge in `MinsRiskBadge`, `set-pieces/SetPieceTakerPanel` already uses `title` attributes. Introducing Radix `<Tooltip>` here would diverge from established convention without an offsetting benefit.
- Mobile long-press shows the tooltip in iOS/Android browsers (verified pattern via existing badges).
- No JS bundle cost, no portal layering issues with the sticky header / sticky first column in `GemTable.tsx`.
- Trade-off accepted: native tooltips are ~500ms delayed and not styleable. This matches the rest of GemTable already.

## Interaction Contracts

### xPts cell hover/tap

- **Desktop hover** on the cell → native browser tooltip surfaces the component breakdown after browser delay (~500ms)
- **Desktop hover** on the variance badge → native browser tooltip surfaces the variance explanation (different `title`, takes precedence because the badge is the more-specific element under the cursor)
- **Mobile tap** on the table row triggers the existing expanded-row behaviour in `GemTable.tsx` line 162 (`if (isMobile) row.toggleExpanded()`) — UNCHANGED by Phase 28. The xPts column is NOT in `HIDDEN_COLUMN_LABELS`, so its number remains in the visible main row.
- **Mobile long-press** on the cell → native browser tooltip surfaces (iOS/Android default behaviour; not customised)

### Variance badge interaction

- Non-interactive — no `onClick`, no `onFocus`, no expand behaviour
- Carries `title` attribute (see VarianceBadge structure) for screen readers and hover/tap explanation
- Sort order: clicking the column header still sorts by the numeric xPts value, NOT by variance — variance is an annotation, not a sort dimension

### GwToggle integration (no behaviour change)

- The existing `<GwToggle value={gwHorizon} onChange={setGwHorizon} />` instance in `GemTable.tsx` line 121 continues to drive which xPts column is visible
- `getColumnVisibility(horizon, isMobile)` in `GwToggle.tsx` is the only location that needs the accessor-key swap (`proj_pts_1gw` → `xPts_1gw`, etc.)
- The toggle pill UI, label "1 GW / 3 GW / 5 GW", and accent colour are UNCHANGED

### Sort behaviour (no behaviour change)

- Default sort remains `[{ id: 'gem_score', desc: true }]`
- Click "xPts" header → sort by `xPts_1gw` desc; second click → asc; third click → none (TanStack default)
- Sort indicator arrow (`▲ / ▼`) inherits the existing `GemTable.tsx` line 147–151 logic — no per-column override
